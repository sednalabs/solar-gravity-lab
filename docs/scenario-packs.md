# Scenario Packs

Scenario packs are deterministic startup scenes for fast Android runtime-mirror
iteration.

They exist so manual testers and automation clients can jump directly to useful
visual situations without rebuilding the app or hand-creating bodies through the
UI each time. The pack selects starting bodies, presentation defaults, focus,
observer mode, and playback posture. Once loaded, the Rust runtime remains
authoritative for world state, commands, checkpoints, physics, and render-scene
export.

## Current built-in packs

- `sol-system`: full canonical startup catalog and the default app scenario.
- `showcase.inner-system`: Sun through Mars plus near-Earth small bodies for
  close-scale navigation and selection polish.
- `showcase.earth-moon`: Earth/Moon framing with marker tracers for trail,
  camera, and paused-inspection work.
- `showcase.jupiter-system`: Jupiter plus Galilean moons and dust markers for
  dramatic orbit framing.
- `showcase.comet-flyby`: planets plus curated comets and a probe for cinematic
  small-body flyby checks.
- `stress.trail-density`: a denser tracer field for legibility and render
  pressure checks. It also crosses the large-scene threshold used by the Arm64
  NEON tiled gravity kernel, making it the preferred built-in pack for checking
  whether large-scene solver-path telemetry becomes visible after load.

## Runtime contract

Scenario packs are fresh-session inputs. Loading a pack replaces the active
runtime session with a new session for that `scenario_id`, seeds the selected
pack through the existing Rust authority command, applies pack presentation
defaults, and then resumes normal runtime-mirror refresh.

Important boundaries:

- Android owns selection UI and session replacement intent.
- Rust owns deterministic body seeding and all mutable world semantics.
- The renderer consumes exported runtime scene packets; it does not define
  scenario truth.
- Pack defaults are presentation defaults, not hidden physics overrides.

## Android usage

The runtime mirror exposes a visible Scenario control with stable test tags.
Automation should operate that same UI instead of out-of-band setup scripts.
This keeps automated actions observable and makes the app behave the same for a
human operator.

Recommended visual iteration loop:

1. Load a focused scenario pack.
2. Use camera, focus, speed, search, and rendering controls until the problem is
   visible.
3. Capture Android screenshots/logs through the hosted session or
   `validation-lab`.
4. Patch the UI/renderer/runtime seam.
5. Rerun the same pack so before/after evidence is comparable.

## Future forecast packs

Scenario packs are also the right place to attach future forecast artifacts.
Those should be generated by validation or build runners as deterministic,
hashable proof artifacts and rendered as non-authoritative assist layers.

Forecast packs should include:

- source commit and scenario id;
- timestep, horizon, precision policy, and backend metadata;
- scalar-oracle or runtime-equivalence evidence;
- content digests; and
- clear telemetry saying the artifact is a visual assist, not authoritative
  runtime truth.

Distributed runners can help generate and validate those artifacts. They should
not be used to split one live emulator interaction loop.
